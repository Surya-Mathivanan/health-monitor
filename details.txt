PROJECT OVERVIEW
────────────────
LifeCare Wellness is a full-stack, browser-based health and call management 
application designed for wellness professionals and clinic staff. It allows 
staff to manage client profiles, track body composition metrics, log calls, 
set follow-up reminders, and write notes — all from a single responsive 
interface that works on phone, tablet, and desktop.

HOW THE APP WORKS — END TO END FLOW
═══════════════════════════════════════════════════════════════════════════════

1. STARTING THE APP
   ─────────────────
   Run: npm run dev
   Opens at: http://localhost:5173

   The app boots via src/main.tsx which wraps everything in:
   - BrowserRouter (React Router v7) for navigation
   - QueryClientProvider (TanStack Query) for data fetching/caching
   - AuthProvider (custom context) which reads the Supabase session

2. AUTHENTICATION FLOW
   ────────────────────
   File: src/features/auth/LoginPage.tsx

   Option A — Google OAuth:
   • User clicks "Continue with Google"
   • Calls supabase.auth.signInWithOAuth({ provider: 'google' })
   • Supabase redirects to Google, then back to /auth/callback
   • AuthCallback.tsx reads the session and upserts a row in public.users
   • User lands on /dashboard

   Option B — Email/Password Login:
   • User enters credentials, form validated with Zod schema
   • Calls supabase.auth.signInWithPassword()
   • On success, navigate to /dashboard

   Option C — Register:
   • Calls supabase.auth.signUp() → Supabase sends confirmation email
   • Also inserts a row into public.users with display_name and role='staff'
   • Role can be 'admin' | 'staff' | 'co_partner' (co_partner is created by
     an admin via the Co-Partners page — they never self-register)

   JWT Handling:
   • Supabase Auth manages JWT tokens entirely
   • Tokens are stored in browser localStorage by Supabase
   • The AuthProvider subscribes to onAuthStateChange to always keep 
     session state current; non-authenticated users are redirected to /login
     by AuthGuard.tsx

3. DASHBOARD (src/features/dashboard/DashboardPage.tsx)
   ──────────────────────────────────────────────────────
   Four KPI cards are loaded in parallel:
   • Total Active Clients     ← SELECT count FROM clients WHERE status='active'
   • Calls This Week          ← SELECT count FROM call_logs WHERE called_at >= week_start
   • Follow-Ups Due Today     ← SELECT count FROM reminders WHERE status='pending' AND due_at = today
   • Reports This Month       ← SELECT count FROM health_reports WHERE recorded_at >= month_start

   Weekly Call Volume bar chart (Recharts):
   • Fetches call_logs for the current week, groups by day of week

   Due Today list:
   • Fetches pending reminders due today, shows quick "Done" button
   • Clicking Done calls completeReminder mutation (PATCH status='completed')

   Recent Activity feed:
   • Reads last 10 rows from audit_logs table (auto-populated by Postgres triggers)

4. CLIENT MANAGEMENT (src/features/clients/)
   ──────────────────────────────────────────
   ClientsPage.tsx:
   • Renders a grid of client cards
   • Search bar uses debounced input → Supabase .ilike('full_name', '%query%')
   • Filter panel: gender, wellness program, active/inactive
   • "Add Client" button opens AddClientModal

   AddClientModal.tsx:
   • Form fields: Full Name, Mobile, Age, Gender, Height, Weight, Wellness Program
   • Validated with react-hook-form + Zod schema
   • On submit: INSERT into clients table
   • On success: navigate to /clients/:id (new client profile)

5. CLIENT PROFILE (src/features/profile/ClientProfilePage.tsx)
   ─────────────────────────────────────────────────────────────
   Header card shows:
   • Avatar (initials-based), name, program badge, status badge
   • Quick stats: mobile, age, height, weight
   • "Call Now" button (see Call Management below)

   Four tabs (scrollable on mobile):
   ┌─────────────────────────────────────────────────────────┐
   │ TAB 1: Latest Report  (LatestReportTab.tsx)             │
   │  Shows the most recent health report with 6 metric cards│
   │  Each card shows value + status flag badge              │
   │  "Log Report" button opens a modal form                 │
   ├─────────────────────────────────────────────────────────┤
   │ TAB 2: Health History  (HealthHistoryTab.tsx)           │
   │  Table of all health reports (oldest → newest)          │
   │  Line chart showing BMI, Body Fat, Visceral Fat trends  │
   ├─────────────────────────────────────────────────────────┤
   │ TAB 3: Call Logs  (CallLogsTab.tsx)                     │
   │  List of all call entries for this client               │
   │  Each card: outcome chip, duration, notes, follow-up    │
   │  "Log call manually" button also opens CallEndedModal   │
   ├─────────────────────────────────────────────────────────┤
   │ TAB 4: Staff Notes  (StaffNotesTab.tsx)                 │
   │  Free-text notes per client, sorted by pinned first     │
   │  Pin/unpin toggle, delete button                        │
   └─────────────────────────────────────────────────────────┘

6. HEALTH REPORT LOGGING
   ──────────────────────
   File: src/features/health/LatestReportTab.tsx

   Staff fills in:
   • Body Fat % · Visceral Fat level · BMI · Resting BMR · Body Age · Skeletal Muscle Mass

   On INSERT into health_reports:
   • A Postgres BEFORE INSERT trigger (compute_health_flags) automatically sets:
     - bmi_status = 'underweight' | 'normal' | 'overweight' | 'obese'
     - visceral_flag = 'normal' | 'high' | 'very_high'
   • No client-side computation needed — the DB handles it

7. CALL MANAGEMENT
   ─────────────────
   File: src/features/calls/

   CallButton.tsx:
   • On mobile: opens tel: link (native phone dialer), then shows modal after 1.5s
   • On desktop: opens CallEndedModal immediately

   CallEndedModal.tsx:
   • Staff selects outcome: Connected / Missed / Voicemail
   • Enters call duration (seconds) and discussion notes
   • Toggle to "Set Follow-up Reminder" — expands date/time picker, title, notes

   On submit (useLogCall hook / useCalls.ts):
   • INSERT into call_logs table
   • If follow-up toggled: INSERT into reminders table, linked_call_id FK set

8. REMINDERS & REALTIME
   ─────────────────────
   File: src/features/reminders/RemindersPage.tsx

   • Shows Pending / Completed / All tabs
   • Overdue reminders highlighted red
   • "Mark Complete" button PATCHes status='completed'

   Realtime sync (useRealtimeReminders hook):
   • Subscribes to Supabase Realtime channel on public.reminders table
   • Any INSERT/UPDATE/DELETE from any session triggers a re-fetch
   • This means if Staff A completes a reminder, Staff B sees it disappear 
     from their Pending list instantly without refreshing

9. NOTIFICATIONS
   ──────────────
   File: src/features/notifications/NotificationBell.tsx

   • Bell icon in TopBar with unread dot indicator
   • Clicking opens a dropdown listing notifications
   • "Mark all read" button PATCHes all unread rows for current user
   • Notifications are inserted by the backend (e.g., staff Edge Functions 
     can write to public.notifications for scheduled follow-up alerts)

10. DARK MODE
    ──────────
    File: src/hooks/useDarkMode.ts

    • Reads localStorage key 'lifecare-theme' on load
    • Falls back to system preference (prefers-color-scheme) if no preference saved
    • Toggling adds/removes 'dark' class on <html> element
    • Tailwind's dark: variant applies dark-mode styles throughout the app

11. USER PROFILE PAGE  ← PREVIOUSLY UNDOCUMENTED
    ─────────────────────────────────────────────
    File: src/features/profile/UserProfilePage.tsx
    Route: /profile (accessible from TopBar avatar)

    Displays and allows editing of the logged-in staff member's profile:
    • Avatar (initials in brand gradient circle)
    • Display Name (editable)
    • Email (read-only — managed by Supabase Auth)
    • Position      e.g. Doctor, Nutritionist, Fitness Coach
    • Personal Number  (their personal contact number)
    • Degree / Qualification  e.g. MD, B.Sc. Nutrition
    • Experience    e.g. 10 years in healthcare

    Edit / Save / Cancel flow:
    • Clicking the pencil icon switches to edit mode
    • On Save: UPDATE public.users SET position, personal_number,
      degree, experience, display_name WHERE id = auth.uid()
    • DoctorProfileCard.tsx renders the read-only card view

12. CO-PARTNERS SYSTEM  ← PREVIOUSLY UNDOCUMENTED
    ─────────────────────────────────────────────
    Files: src/features/copartners/CoPartnersPage.tsx
           src/hooks/useCoPartners.ts
    Route: /co-partners

    What it does:
    Allows a staff member (supervisor) to add "co-partners" — other staff
    users whose client lists they can monitor. Each co-partner has their own
    login and manages their own clients independently; the supervisor can only
    VIEW (not edit) those clients.

    The Page has 3 sections:
    ┌─────────────────────────────────────────────────────────┐
    │ KPI Cards                                               │
    │  • Active Partners count                                │
    │  • Total clients under all partners                     │
    │  • Pending requests count                               │
    ├─────────────────────────────────────────────────────────┤
    │ Received Invitations Banner                             │
    │  Polls every 30s. Shows partner requests from others.   │
    │  Accept / Decline buttons per invitation.               │
    ├─────────────────────────────────────────────────────────┤
    │ Pending Requests (sent by me, awaiting response)        │
    │  Each row: invitee email, time sent, Cancel button      │
    ├─────────────────────────────────────────────────────────┤
    │ Active Partners list                                    │
    │  Search bar (visible when >3 partners)                  │
    │  Each card: avatar, name, email, client count           │
    │  Buttons: View (drill-in) / Remove (with confirm)       │
    └─────────────────────────────────────────────────────────┘

    Add Co-Partner — 2-Step Modal (InviteModal.tsx inside CoPartnersPage):
    Step 1: Enter email → "Check Email" button
      → Queries public.users for that email
      → Found:     shows user name + "Send Partner Request" button
      → Not found: shows "Create Account for Them" button
    Step 2a (existing user): Confirm card → "Send Request"
      → INSERT into co_partner_invitations status='pending'
      → They see it in their Received Invitations banner
    Step 2b (new user): Create form (display_name, email, password)
      → "Create & Link" button
      → Uses a TEMPORARY Supabase client (persistSession: false)
        to call auth.signUp() without replacing the admin session
      → Calls RPC register_new_co_partner() to insert public.users
        row + accepted invitation in one SECURITY DEFINER transaction

    Partner Detail View (CoPartnerDetail component):
    • Drill-in from partner card → back button to list
    • Header: avatar, name, email, join date, client count
    • Searchable client list (read-only, shows gender/age/mobile/status)

    Hooks exported from useCoPartners.ts:
    • useCheckEmail(email)            → lookup by email
    • useCoPartners()                 → accepted partners list with client counts
    • useSentPendingInvitations()     → invitations I sent, still pending
    • useReceivedInvitations()        → invitations sent to me, pending
    • useCoPartnerClients(partnerId)  → clients belonging to a partner
    • useSendInvitation()             → INSERT invitation for existing user
    • useCreateCoPartner()            → signUp + RPC (isolated temp client)
    • useAcceptInvitation()           → RPC accept_co_partner_invitation()
    • useDeclineInvitation()          → RPC decline_co_partner_invitation()
    • useRemoveCoPartner()            → DELETE invitation row
    • useCoPartnersSummary()          → KPI totals for dashboard

DATABASE TABLES AND THEIR PURPOSE
═══════════════════════════════════════════════════════════════════════════════

users              → Mirrors Supabase Auth. Stores display_name, avatar_url, role
                     role = 'admin' | 'staff' | 'co_partner'
                     Extended profile columns (for UserProfilePage):
                       position, personal_number, degree, experience

wellness_programs  → Seeded with 6 programs (Weight Loss, Muscle Gain, etc.)
                     Staff can assign a program to each client

clients            → Core client record: demographics, height, weight, program
                     status = 'active' | 'inactive'
                     created_by (UUID FK → users.id) — tracks which staff
                     member owns each client. Used for co-partner RLS isolation.

health_reports     → One row per body scan / measurement session
                     Postgres trigger auto-fills: bmi_status, visceral_flag

call_logs          → One row per call made. Links to reminders via linked_call_id

reminders          → Scheduled follow-up tasks. Realtime publication enabled.
                     status = 'pending' | 'completed' | 'snoozed'

staff_notes        → Free-text notes per client, authored by a staff member
                     is_pinned = true floats notes to the top

notifications      → In-app alerts per user. Realtime publication enabled.
                     type = 'follow_up' | 'system'

audit_logs         → Automatic write log. Every INSERT/UPDATE/DELETE on key 
                     tables is recorded here via Postgres trigger

co_partner_invitations  ← PREVIOUSLY UNDOCUMENTED
                     Manages supervisor–partner relationships.
                     inviter_id  → the supervisor (staff/admin)
                     invitee_email / invitee_id → the co-partner
                     status = 'pending' | 'accepted' | 'declined'
                     UNIQUE(inviter_id, invitee_email)
                     RLS: inviters see sent rows; invitees see received rows

═══════════════════════════════════════════════════════════════════════════════
SECURITY MODEL
═══════════════════════════════════════════════════════════════════════════════

• Every table has Row Level Security (RLS) enabled
• Staff users can only see their OWN clients (created_by = auth.uid())
• Co-partners can only see their own clients — no cross-visibility
• Supervisors (inviters) can see their co-partners' clients, health_reports,
  call_logs, staff_notes, and reminders (via co_partner_invitations lookup)
• Admin role bypasses all restrictions via is_admin() Postgres function
• is_co_partner() helper function checks role = 'co_partner'
• .env file is gitignored — credentials NEVER go to Git
• Creating a co-partner account uses a temp Supabase client
  (persistSession: false) to prevent the admin session being overwritten

SETUP STEPS (QUICK REFERENCE)
═══════════════════════════════════════════════════════════════════════════════

1. npm install
2. Create Supabase project at https://supabase.com
3. Run SQL files in Supabase SQL Editor in order: 001 → 002 → 003 → 004 → 005 → 006 → 007
4. Copy .env.example to .env, fill in VITE_SUPABASE_URL + VITE_SUPABASE_ANON_KEY
5. (Optional) Enable Google OAuth in Supabase Auth → Providers → Google
6. Disable email confirmation in Supabase Auth → Settings → Email
   (Required for Co-Partners: Create & Link flow works without confirmation)
7. npm run dev → http://localhost:5173
